CodeMender CI Lab — GitHub Actions Guardrail

A security guardrail wired into GitHub Actions. On every push, CodeMender scans OWASP Juice Shop, verifies which findings are real by reproducing the exploit against the running app, generates a fix and opens a pull request, and blocks the deployment until an un-dismissed HIGH/CRITICAL is resolved. CodeMender proposes the change — a human reviews and merges. The hands-on lab runs as a self-paced Qwiklab; this page explains the pipeline first.

⏱ ~30–90 min ◆ Intermediate ⚙️ GitHub Actions · ubuntu-latest 🛡️ scan · verify · fix · PR 📄 Public preview docs
🛡️ It proposes fixes — a human merges them

After confirming a finding is real, CodeMender cm fix generates and build-tests a patch, and the pipeline opens a codemender/fix-* pull request (it needs contents: write + pull-requests: write). It never merges on its own — you review the diff, and the Security Gate keeps the deploy blocked until the fix lands on main.

How it works

The whole guardrail is one GitHub Actions workflow (.github/workflows/codemender-pipeline.yml) plus two small Python helpers. CodeMender is a cloud service with a local executor: the cm binary uploads in-scope source and streams commands, but the reasoning — and the exploit reproduction — is driven server-side.

  • Trigger — every push to main, or a manual Run workflow with a verify_limit input. Doc-only changes (**.md, lab/**) are ignored so they don't kick off a long scan.
  • Authenticate — a service-account key (the GCP_SA_KEY secret) is activated for gcloud and exported as ADC, authenticating both the binary download and CodeMender's Vertex AI calls; CM_PROJECT selects the entitled project.
  • Install cm — gcloud artifacts generic download pulls the cm binary from Google's Artifact Registry.
  • Install the app — actions/setup-node + npm install, so cm verify can actually build and run Juice Shop later.
  • Scan — cm find "$(realpath routes)" -y uploads the in-scope source to CodeMender on Vertex AI; a server-side agent reasons about vulnerabilities and records the findings. The absolute scan path makes findings carry absolute file paths so verify can resolve them.
  • Triage — cm_triage.py parses cm report -f json, counts HIGH/CRITICAL, ranks them, and selects the top N (VERIFY_LIMIT, default 1) to verify.
  • Verify — cm verify <id> --bypass-warning, looped over the triaged findings, starts the app and fires a proof-of-concept exploit. Each finding becomes VERIFIED DISMISSED or inconclusive (time-boxed).
  • Fix — cm fix <id> --bypass-warning, looped over every un-dismissed finding, generates + build-tests a patch and writes it into the working tree (PER_FIX_TIMEOUT per finding).
  • Open PR — the patched files are committed to a codemender/fix-<run id> branch and gh pr create opens one PR whose body is CodeMender's report.
  • Gate — the Security Gate step turns the run red and blocks the deployment on any HIGH/CRITICAL that verify did not explicitly dismiss — until the fix PR is merged.
🔑 What authenticates

A service account (the GCP_SA_KEY secret) is CodeMender's credential: it authorizes the Artifact Registry binary download and, exported as ADC, CodeMender's calls to Vertex AI (aiplatform.googleapis.com). CM_PROJECT is the preview-entitled project it runs against. The built-in GITHUB_TOKEN is used only to push the remediation branch + open the PR.

⚠ One-time repo setting for the PR

Opening a PR with GITHUB_TOKEN requires Settings → Actions → General → Workflow permissions → "Allow GitHub Actions to create and approve pull requests." Without it, the "Open Remediation PR" step fails with "GitHub Actions is not permitted to create or approve pull requests."

🎲 Verdicts vary — that's expected

Verification is a slow, server-side agent loop. A finding can have its exploit reproduced but not finalize a VERIFIED stamp within the time-box, landing inconclusive. The gate treats anything not explicitly DISMISSED as still-blocking, so an unfinished verify never lets a real vulnerability through.

⚙️ Tuning the agent: --model and -c

The pipeline's cm find / cm verify / cm fix calls accept --model <name> (pick a faster flash or a deeper pro model — see the preview docs for the current list) and -c "<context>" (pass extra context to the agent). To customize, edit those command lines in the workflow — or wire them as workflow_dispatch inputs.

⚠ Why there's no --fail-on=high,critical flag

The real cm has no such flag — a scan exits 0 whether or not it finds bugs. The gate is something you build: parse cm report -f json and fail the job yourself. That's the transferable pattern for wiring any scanner into a pipeline.

🚨 How the gate decides — and why it stays red

The gate is a fail-safe. It computes BLOCK = high_critical − dismissed and fails the run red whenever BLOCK > 0 — i.e. unless every HIGH/CRITICAL finding was explicitly DISMISSED by verify (a VERIFIED or an inconclusive verdict still blocks; the verified count is informational only). Two things follow:

  • high_critical is the whole scan's count, but dismissed only reflects the top-N that verify examined (VERIFY_LIMIT, default 1). So with ~9–13 findings the gate essentially always blocks in the default lab — green requires verifying and dismissing them all.
  • Opening the fix PR does not turn the gate green — main stays vulnerable until you review and merge it, then re-run. The gate only appends a hint pointing at the PR.

What you'll do in the lab

The Qwiklab provisions a repo (a Juice Shop fork with the pipeline already wired) and the credentials. Your job is to operate the guardrail and review what it proposes:

  1. Open the Qwiklab — it hands you the lab repo and (from your instructor) a service-account key + project id.
  2. Add the secrets — under Settings → Secrets and variables → Actions, add GCP_SA_KEY (the service-account JSON) and CM_PROJECT (the entitled project id) — ask your instructor for both.
  3. Enable PR creation — Settings → Actions → General → Workflow permissions → "Allow GitHub Actions to create and approve pull requests."
  4. Trigger the pipeline — push to main, or Actions → Run workflow and (optionally) set verify_limit.
  5. Watch scan → verify → fix → PR — the Verify Findings and Remediate Findings logs show the app booting and the exploit / fix attempts against localhost:3000.
  6. Review the PR & results — open the codemender/fix-* pull request and read its diff; download the codemender-report artifact and the run Summary (Triage / Verify / Remediation), and confirm the red Security Gate blocked the deploy.
