Build a CodeMender remediation pipeline on GitHub Actions

You'll package CodeMender into a container, push it to GHCR, and hand-write a GitHub Actions workflow that scans OWASP Juice Shop, verifies a real vulnerability, fixes it, and opens a Pull Request on your own fork — which you review, approve, and merge.

⏱ ~45 min ◆ Intermediate ⎇ GitHub · Actions · GHCR · Packages 🔑 1 secret (a PAT)
🔄 This is the GitHub Actions port of the Cloud Build lab

Same CodeMender, same four phase scripts — a different CI driver. The interesting part is what disappears: because every step of a GHA job runs in one container, the CodeMender state that Cloud Build had to persist in a gcsfuse-mounted GCS bucket now just lives on the job filesystem. No bucket, no gcsfuse, no GCP.

The big pictureWhat you are building

CodeMender (cm) is an AI security agent: a thin client that streams a codebase to a hardened backend which reasons about vulnerabilities and generates validated patches. You'll drive it from CI as five steps of a single GitHub Actions job:

  • clone — shallow-clone your fork into /workspace/repo using your PAT.
  • find — cm find scans a file and records vulnerabilities (severity, CWE, analysis).
  • verify — cm find verify reproduces the top finding (it may build & run the app) to confirm it's real. This is why the image ships with node/npm.
  • fix — cm fix generates the patch; your script applies it deterministically.
  • open-pr — commit to a branch, push to your fork, open a PR whose body is CodeMender's own analysis.
💾 Why there's no state bucket here

On Cloud Build each step is a fresh container, so CodeMender's ~/.codemender (config, identity key, findings SQLite DB) had to be persisted in a gcsfuse-mounted GCS bucket. On GitHub Actions every step of a job runs in the same container, so that directory simply survives from find to verify to fix. We point $HOME at a per-run folder and move on — the one real simplification of this port.

🔑 No CodeMender secret to manage — for now (EAP)

The CodeMender server endpoint and credential are baked into the cm binary, so the only secret you create is a GitHub token to push and open a PR. That's an EAP convenience. The public preview and GA won't ship auth in the binary — they'll authenticate with standard methods you wire into the same one setup step: a service account, Workload Identity Federation, or a scoped API key (least secure of the three). See Production & EAP notes.

The five scripts — identical to the Cloud Build lab

The CodeMender knowledge lives in the container image and four phase scripts. Those are byte-for-byte the same across platforms. Only cm-env.sh (the shared setup the others source) changed — its gcsfuse mount block is gone, because state persistence is free here:

  • cm-env.sh — not a step of its own. It points $HOME at a per-run folder, runs cm init once, and defines top_finding_id(), the jq helper that picks the highest-severity finding. find/verify/fix each source it first.
  • find.sh → verify.sh → fix.sh → open-pr.sh — one workflow step each, run in order, all in the same container.

In sync without passing arguments. No step tells the next which finding to work on. Every step independently re-runs top_finding_id() — it greps cm report -f json, keeps findings at or above MIN_SEVERITY, and returns the single top one. Because all steps read the same findings DB on the shared filesystem, they agree on the same finding without ever exchanging an ID. That decoupling is why any step can be re-run on its own, and why the “confirm remediation” pass naturally opens no PR once the top finding is gone.

Why it's built this wayDesign decisions

DecisionWhy
One job, five steps (not five jobs)Steps of a job share a container and filesystem, so CodeMender state persists for free. Splitting into jobs would reintroduce the cross-container state problem (and need actions/cache or artifacts).
Container image from GHCRThe image is the transferable unit: the same Dockerfile runs on Cloud Build, GHA, and GitLab, and pins the exact toolchain (node 22, build-essential) regardless of the runner. Pulled with the built-in GITHUB_TOKEN — no registry credentials to manage.
Full verification, not skippedCodeMender reproduces the exploit (it builds & runs the app), so a fix targets a confirmed bug. This is why the image ships node/npm and why verify is the slow step.
15-min verify cap + PR flagcm find verify is thorough but variable. The cap is a lab convenience, not a product limit. When it's hit we still generate the fix and flag the PR as UNVERIFIED so the human reviewer scrutinises it. Automated verification assists the human gate — it never replaces it.
Deterministic patch applyThe fix step prefers the change CodeMender actually made to the target file, falling back to its stored patch — so the result is reproducible.
Human-in-the-loop PRThe pipeline never writes to master. CodeMender proposes; you review, approve, and merge. Nothing in the pipeline ever closes a PR, so the review PR stays open until a person acts on it.
Same-file concurrency guardA concurrency: group serialises runs that target the same file, so two cm fix runs never produce divergent patches / conflicting PRs. See Concurrency & safety.
Single-file scan targetA one-file target keeps CodeMender's sandbox scoped — fast and deterministic for the lab.
Severity gate (min_severity, default CRITICAL)Only findings at/above the threshold are auto-remediated. Lower-severity findings are reported but don't open PRs.

Before you startPrerequisites

You drive this lab from your own laptop and your own GitHub account. The heavy lifting — building the image, running CodeMender, opening the PR — happens on GitHub-hosted runners, so you need no local Docker and no GCP. What you do locally is set up the repo and push the files into it.

You needNotes
Your GitHub accountYou'll fork Juice Shop and host the pipeline repo under it. GHCR (Packages) is included — nothing to enable.
git + gh on your laptopTo create the repo, add the files (including the cm-linux binary), and push. gh also powers the optional copy-paste commands; anything gh does you can also do in the GitHub web UI. (install gh, then gh auth login.)
The CodeMender binary (cm-linux)Provided by your facilitator during EAP. You commit it into your repo and bake it into the image in Step 5. (At public preview you'll download your own.)
⚠ Use a throwaway fork

Juice Shop is deliberately vulnerable. Keep it in an isolated fork; never expose it publicly.

The transferable unitThe CodeMender image

The toolbox image is a deliberately minimal container: the cm client plus the build/runtime tools the pipeline needs (node/npm so cm find verify can build & run Juice Shop, git, jq). It carries no orchestration — you author the scripts and the workflow.

It's identical to the Cloud Build lab's image (it even still contains gcsfuse — harmless here, and it keeps one image working across every platform). You build it once with the workflow in Step 5; here's the recipe for reference:

container/Dockerfile — reference only ▸
1

Fork Juice Shop

Fork OWASP Juice Shop into your account — this is the code CodeMender will scan and open a PR against. Base branch is master.

2

Create the pipeline repo

The workflow lives in its own repo (kept separate from the code it scans, mirroring how you'd run a remediation pipeline against many targets). Create a private repo and add these files — the layout you'll fill in over the next steps:

Create it and clone it to your laptop, then you'll add these files over the next steps and push. (Prefer the browser? Create the repo on github.com and use Add file → Upload files instead — but the cm-linux binary is ~29 MB, so pushing with git is smoother.)

3

Create a fine-grained PAT

The pipeline's job-scoped GITHUB_TOKEN can't reach a different repo, so the open-pr step needs a token that can push a branch and open a PR on your fork. Create a fine-grained personal access token scoped to just that fork:

  • GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
  • Repository access → Only select repositories → your juice-shop fork.
  • Repository permissions: Contents: Read and write Pull requests: Read and write
  • Set a short expiry and generate. Copy the token — you'll paste it in Step 4.
🔑 Why not the built-in token?

GITHUB_TOKEN is automatically scoped to the repo the workflow runs in (the pipeline repo), so it can't push to your fork. A scoped PAT is the least-privilege way to cross that boundary. (If you put the workflow inside the fork instead, GITHUB_TOKEN would suffice — but keeping the pipeline in its own repo is the more portable, real-world shape.)

4

Set the GH_PAT secret

Store the token as an Actions secret named GH_PAT in the pipeline repo. This is the GHA equivalent of the Cloud Build lab's Secret Manager gh-pat.

5

Build the toolbox image → GHCR

Add container/Dockerfile and the cm-linux binary, then add this workflow. It builds the image and pushes it to GHCR using the built-in GITHUB_TOKEN (granted packages: write) — no local Docker, no registry login, no GCP.

Run it: Actions → build-image → Run workflow. It finishes in ~90 s and produces ghcr.io/YOUR_USER/codemender-ci:v0.2.0. The package is private and linked to the repo, so the pipeline pulls it with the same GITHUB_TOKEN.

6

Write the phase scripts

Four of the five scripts are identical to the Cloud Build lab — copy find.sh, verify.sh, fix.sh, and open-pr.sh unchanged into scripts/. They're pure CodeMender logic and don't care what CI drives them. The only edit is cm-env.sh: its gcsfuse mount block is gone, because state persists on the job filesystem.

The four unchanged scripts — full source (copy into scripts/) ▸
ScriptDoes
find.shsource cm-env.sh; cm find $SCAN_PATH -y; write cm report -f json; pick the top finding.
verify.shcm find verify the top finding under a 15-min timeout; record the verdict (VERIFIED / OPEN) to a hand-off file. Hitting the cap does not skip fix.
fix.shcm fix --auto-apply; prefer the change made to the target file, else apply the stored patch; write cm-status.txt (FIXED / DISMISSED / NONE).
open-pr.shIf FIXED: commit to codemender/<cwe>-<id>, push with GH_TOKEN, open a PR whose body is CodeMender's analysis (flagged UNVERIFIED if verify hit the cap).

These are identical to the Cloud Build lab — copy each into scripts/ exactly as-is. Only cm-env.sh (above) differs.

7

Write the workflow

This is the driver — the GHA counterpart of cloudbuild.yaml. One job, running inside the toolbox container, with the five steps as run: steps. Note three things: the container: block (pulls from GHCR with GITHUB_TOKEN), the concurrency: guard (same-file safety), and STATE_ID: ${{ github.run_id }} (per-run state isolation).

8

Run the pipeline

Actions → codemender → Run workflow. Keep the defaults (scan routes/login.ts) or set min_severity. Watch the steps stream in the job log.

📈 What "success" means on each step

The step goes green if its script exits 0. For verify that includes the case where the 15-min cap was hit — the pipeline proceeds and flags the PR UNVERIFIED. Green on verify is not the same as “CodeMender confirmed it”; read the PR banner.

9

Review the fix & the PR

The open-pr step logs the PR URL. Open it on your fork: the body is CodeMender's own analysis (finding, severity, confidence, verification verdict) and the diff. For the default routes/login.ts target the fix replaces a raw SQL string with a parameterised query — the correct SQL-injection remediation.

⚠ The commit may touch more than the scan file

To reproduce the exploit, cm find verify can edit other files (e.g. disabling a startup precondition so the app boots). Because open-pr.sh commits all tracked modifications (git add -u), that scaffolding can ride along in the PR. Review the full diff. To scope the commit to just the finding's file, change git add -u to git add -- "$FILE" in open-pr.sh — a good hardening.

10

Approve & merge the Pull Request

You are the gate. Read the analysis, confirm the diff, then Merge. The pipeline never writes to master and never closes the PR — it stays open until you act, so a reviewer always makes the final call.

11

Confirm the remediation

Re-run the workflow after merging. find re-scans the now-fixed file; top_finding_id() finds nothing at/above the gate, so fix writes NONE and open-pr logs “nothing to open a PR for.” A clean confirm run — no PR — is the proof the vulnerability is gone.

ReferenceConcurrency & same-file safety

Two cm fix runs working the same source file at once would generate divergent patches, race on the branch, and open conflicting PRs. The workflow closes all three race surfaces:

Race surfaceGuard
The target file / branchconcurrency: group keyed by (owner, repo, scan_path) with cancel-in-progress: false — same-file runs queue and run one at a time; different files still run in parallel.
CodeMender state DBSTATE_ID = github.run_id → each run gets its own ~/.codemender, so the findings SQLite DBs never collide.
The working treeEach run clones the fork fresh into its own container filesystem — no shared checkout to corrupt.

Scaling to many files? Drive a matrix over scan paths and set the concurrency group from matrix.scan_path. Same-file legs serialise; different-file legs run concurrently — safe fan-out with no extra machinery.

Beyond the labProduction & EAP notes

The lab is deliberately transparent so you see every step. A real deployment would harden it:

  • CodeMender auth (post-EAP). The baked-in credential goes away at public preview. Wire auth into the one cm init step in cm-env.sh — a service account, Workload Identity Federation (keyless; GHA issues an OIDC token GCP can federate), or a scoped API key stored as another Actions secret. WIF is the most portable and needs no long-lived secret.
  • Scope the commit. Change git add -u to git add -- "$FILE" so verification scaffolding can't ride along in the PR (see Step 9).
  • Pin the image by digest (@sha256:…) instead of a tag, and least-privilege the PAT (fine-grained, short expiry) or use a GitHub App.
  • Emit SARIF (cm report -f sarif) into GitHub code scanning instead of ad-hoc jq parsing.
  • Put the workflow in the target repo to drop the PAT entirely (native checkout + GITHUB_TOKEN for the PR) — less portable across CIs, but simplest when you guard a single repo.
  • Set build.command so cm rejects patches that don't compile/test, and widen scans from a file to a directory.

Wrap upCleanup

CodeMender CI Lab — GitHub Actions variant. Same CodeMender, same scripts; a thinner driver and one less moving part. Built and validated end-to-end: image pushed to GHCR, one-job pipeline opened a real PR on a Juice Shop fork, CodeMender state persisted across steps with no gcsfuse.
