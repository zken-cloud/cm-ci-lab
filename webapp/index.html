CodeMender CI Lab — Public Preview (Cloud Build)

Scan OWASP Juice Shop, verify a real vulnerability, fix it, and open a PR — driven by the public-preview CodeMender CLI in a Cloud Build pipeline. No baked image credential: cm authenticates as the pipeline's own identity and runs against the shared, preview-entitled project cloud-llm-preview1.

⏱ ~40 min ◆ Intermediate ☁ GCP · Cloud Build · Artifact Registry · GCS ⎇ GitHub
✓ Verified vs ⚠ not-yet-verified

verified steps have been run for real. unverified steps follow directly from what works but the full Cloud Build pipeline has not been run end-to-end yet — this run is the one that proves it. The interactive path (download → cm init → cm find) is verified in cloud-llm-preview1 with a @google.com identity.

⚠ The one thing this run is testing

The pipeline runs cm as cloud-llm-preview1's Cloud Build service account, not a human. We confirmed a service account clears the Interaction API's IAM check and provisioning; what is not yet confirmed is that the build SA is entitled to the codemender-preview agent. If Step 10 fails with Unsupported agent interaction: codemender-preview, that entitlement is the gap — see Step 10.

◆

How it works

Five Cloud Build steps in cloud-llm-preview1, one script each — a fifth, cm-env.sh, is sourced by the others so they share one setup and one finding-selector. CodeMender is local-first: a hosted agent reasons; the cm client reads files, builds, and runs proof-of-concept exploits locally.

  • find.sh — cm find scans many files (a directory or a list) and records every finding.
  • verify.sh — fans out cm verify across the found vulnerabilities, _VERIFY_FANOUT at a time.
  • fix.sh — fans out cm fix across the verified vulnerabilities, _FIX_FANOUT at a time.
  • open-pr.sh — applies the collected patches and opens one PR whose body is CodeMender's analysis.
🗄️ Why the state bucket — and why fan-out copies it

Each Cloud Build step is a fresh container, so CodeMender's findings state.db (SQLite, under ~/.codemender) is carried across steps in a gcsfuse-mounted GCS bucket. But SQLite is single-writer and gcsfuse advisory locks are unreliable, so the fan-out workers in verify/fix must not write that shared DB in parallel — each copies it to local disk and runs in its own independent clone. That isolation is what makes _VERIFY_FANOUT / _FIX_FANOUT safe. (On a single-container runner like GitHub Actions the bucket isn't needed.)

⚠ Use the right build SA

A project has two build identities: the legacy PROJNUM@cloudbuild.gserviceaccount.com and the default PROJNUM-compute@developer.gserviceaccount.com. In testing, only the compute SA carried the AI roles — the legacy cloudbuild SA was denied aiplatform.interactions.create. The pipeline below pins the entitled SA with --service-account (Step 10). Your facilitator will tell you which SA in cloud-llm-preview1 is entitled.

ℹ Because the project is shared, namespace everything

Buckets and secrets live in one project for the whole cohort, so name them with your ldap to avoid collisions: ldap-cm-state, gh-pat-ldap, branch codemender/fix-ldap. Your Juice Shop fork is on your own GitHub, so PRs never collide.

Write the phase scripts

Five scripts under scripts/ (four steps + the sourced cm-env.sh). Preview command surface: cm verify, cm fix -y, cm report --format json. No auth step — the build SA is the ADC identity.

⚡ Two knobs control fan-out

_VERIFY_FANOUT — how many found vulnerabilities verify.sh reproduces in parallel. _FIX_FANOUT — how many verified vulnerabilities fix.sh patches in parallel. Each worker runs in a private state copy + an independent git clone (a worktree shares .git and deadlocks).

⚠ Validated: fan-out is port-bound on a single-server app — default is 1

Testing with a real binary confirmed two things. The clone isolation above is required (worktrees collide on .git/index.lock). And cm verify/cm fix build & run Juice Shop on a fixed port (3000) to reproduce the exploit — so two in parallel collide on the port regardless of git isolation. For one target, keep both fan-outs at 1. Raise them only when workers have isolated runtime (distinct targets, or per-worker network namespaces), or fan out static verification with cm verify --skip-exploit-verification (no app, no port). The machinery scales; the single shared app is the limit.

Facilitator notes

  • Everything runs in cloud-llm-preview1. Grant each participant roles/cloudbuild.builds.editor and iam.serviceAccountUser on the entitled build SA so they can submit builds that run as it.
  • Confirm the build SA is agent-entitled. The project is entitled; verify the compute SA specifically can call the codemender-preview agent (a single cm find in a one-step build). This is the one unproven link.
  • Build the toolbox image once and share its URL — it carries no credential, so a shared image is fine.
  • Namespacing is mandatory in a shared project: per-ldap buckets, secrets (gh-pat-ldap), and PR branches. STATE_ID=$BUILD_ID already isolates state per run.
  • Access is @google.com-only for now (Googlers), inherited from the shared project. Customer/Argolis projects need their own preview entitlement before this model extends to them.
