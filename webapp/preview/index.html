CodeMender CI Lab — Public Preview edition

The same lab — scan Juice Shop, verify a real vulnerability, fix it, open a PR — rebuilt on the public preview CodeMender CLI. Participants now download the CLI themselves and authenticate with their own Google Cloud credentials, so the central shared image disappears.

⏱ ~60 min ◆ Intermediate ☁ GCP · Cloud Build · Artifact Registry · GCS ⎇ GitHub
⚠ Staging draft — not yet runnable

CodeMender's public preview documentation is live, but access is not. The docs state the CLI is "available to a limited set of customers in Public Preview — contact your sales team to get access." Until our identities are allowlisted, every command below is written from the documentation and has not been executed. Treat this page as the migration plan, not a tested lab. The EAP lab remains the one you deliver today.

What changes from the EAP lab

The preview changes the trust model, not the teaching arc. The lab still walks a CE through find → verify → fix → PR by hand; what changes is where the binary comes from and who the caller is.

✓ The big win: the lab stops handling a secret

Today's lab exists inside a compromise — the image carries an unrotatable key, so access must be granted per-SA and revoked after every cohort, and a leak is unfixable. In preview that entire problem disappears: the artifact is inert and each caller authenticates as themselves. Sections of the EAP guide devoted to protecting the image can simply be deleted.

How it works

The preview CLI is local-first: a hosted agent does the reasoning, and the CLI on your machine executes the file reads, builds, and proof-of-concept exploits. documented

  • Your source is never uploaded in bulk. Only targeted snippets, findings, proposed patches, and command results go to the backend.
  • Session data is retained at most 7 days, and can be deleted immediately via DeleteInteraction.
  • Findings are ephemeral — they accumulate in memory during the pipeline rather than in a long-lived store.
  • VPC Service Controls are supported, so the perimeter story holds for regulated customers.
ℹ Why the four Cloud Build steps stay

Findings still live in a local SQLite state.db. Each Cloud Build step is a fresh container, so the state would vanish between find and fix — the gcsfuse-mounted bucket from the EAP lab is still the mechanism that carries it. (On a single-container runner such as GitHub Actions, this is unnecessary.)

Write the phase scripts

Four small scripts, one per phase — the same shape as the EAP lab, with the preview command surface. Create them under scripts/.

⚠ Two guesses live in that file

The config block sets both confirm_execution and confirm_writes because the docs reference each in a different place (Open question 7) — harmless if one is ignored. And top_finding_id assumes --format json emits an array of objects with a FindingID field, which is the EAP shape; the preview JSON schema is not documented. Check both against real output before a cohort.

The EAP lab capped this step at 15 minutes because verification builds and runs the whole app. Keep that cap — and note the preview adds --skip-exploit-verification for a static-only pass, which is a useful escape hatch if a cohort is running long.

✓ The EAP patch dance is gone

The EAP lab had to re-apply a stored patch by hand, because cm fix could reset the tree and --export was unimplemented. The preview documents cm fix as applying the validated patch to your workspace, with cm vcs status|diff|stage|reset to inspect it — so fix.sh gets materially simpler. assumed that no fallback is needed; keep an eye on it in the first real run.

cm report --format md is new in preview — GitHub-flavored Markdown, which is exactly what a PR body wants. The EAP lab had to assemble one from JSON.

Authenticating in CI — ADC is not a blocker

The docs only show gcloud auth application-default login, which looks like an interactive dead end for a pipeline. It isn't. ADC is a credential resolution chain, not a login method — that command is just the laptop way to populate it. Libraries resolve credentials in this order:

#ADC looks forWho uses it
1GOOGLE_APPLICATION_CREDENTIALS → a JSON file (SA key or a Workload Identity Federation config)CI outside GCP
2The well-known file written by gcloud auth application-default loginLaptops
3The metadata server — the attached service accountCloud Build, Cloud Run, GCE, GKE
✓ Verified: on Cloud Build, path 3 needs zero configuration

A real build in this project confirmed it — no ADC file on disk, GOOGLE_APPLICATION_CREDENTIALS unset, and google.auth.default() still returned working credentials for 163236863044@cloudbuild.gserviceaccount.com, minted a token, and auto-detected the quota project. The build service account simply is the ADC identity. Nothing in the pipeline needs an auth step.

Options by platform

Where the pipeline runsHow to authenticateVerdict
Cloud Build (or Cloud Run / GKE / GCE)Nothing. Metadata server resolves the attached SA. Attach a custom SA via the build's serviceAccount: field for least privilege.best no key material anywhere

Same, without WIFA service-account key JSON in a CI secret, written to a file, pointed at by GOOGLE_APPLICATION_CREDENTIALS.works, but see below

⚠ Don't undo the win with a key file

The headline improvement of preview is that no long-lived credential ships in the artifact. Dropping an SA key JSON into a CI secret re-creates exactly the problem we just escaped — a static, stealable, manually-rotated credential — only now it's in your CI system instead of a container. Use WIF unless something genuinely blocks it.

⚠ Authentication is not authorization

Everything above solves proving who you are. It says nothing about whether that identity is allowed to call CodeMender. The docs gate preview on an allowlist and never say whether service accounts can be on it — that is still Open question 1, and it remains the one that decides whether a CI lab is possible at all. A build SA that authenticates perfectly and is then refused by the allowlist looks like a broken pipeline, so establish this before a cohort.

ℹ Watch the quota / billing project

The docs say data is isolated per customer billing project. In CI the quota project resolves automatically to the build project (verified above). On a laptop it may not — if a user hits quota-project errors, gcloud auth application-default set-quota-project PROJECT_ID is the fix.

cm cheat sheet — public preview

CommandWhat it does
cm init / cm init --verifyCreate local state; --verify tests backend connectivity
cm find PATH [-y]Scan a file or directory. Docs recommend 10–50 files at a time
cm verify FINDING_IDBuild and run a PoC exploit to confirm exploitability
cm verify ID --skip-exploit-verificationStatic verification only — much faster
cm fix FINDING_ID [-y]Generate, build-test, and apply a patch
cm fix ID --no-cacheForce a fresh patch instead of a cached one
-c / --context "…"Steer verify/fix with domain context or coding standards
--model MODELgemini-3.5-flash (default), gemini-3.1-pro-preview, gemini-3-flash-preview
cm report [--format table|html|md|json|sarif]Findings report; --open launches HTML in a browser
cm report --severity|--status|--session|--sortFilter by CRITICAL…LOW, OPEN/FIXED/DISMISSED/REOPENED, session, severity or time
cm report --patches|--artifactsInclude full diffs; include agent logs and exploit scripts
cm vcs status|diff|stage|resetInspect, stage, or discard CodeMender's changes

✓ SARIF is the production story

cm report --format sarif emits SARIF v2.1.0 — feed it into Security Command Center or GitHub code scanning instead of parsing JSON with jq. That is the single best "what would you do for real?" talking point in the lab.

Facilitator notes

  • Your delivery job shrinks to almost nothing. No image to publish, no per-SA grants to collect, no revocation sweep afterwards. What replaces it is getting the cohort's identities onto the preview allowlist — do that well before lab day, since we don't yet control the lead time.
  • Re-verify the whole lab when access lands. Every command here is transcribed from documentation, not run. Budget a full end-to-end pass before you put it in front of anyone.
  • Keep the EAP lab live until then. It is tested and it works; this page is the successor, not the replacement.
  • Watch the severity gate. Findings and severities are model-assessed and re-derived per scan, so a run can legitimately produce nothing at CRITICAL. That was true in EAP and there is no reason to expect otherwise here.

Cleanup

Your image lives in your own project — delete the codemender repo too if you're tearing the project down. There are no cross-project grants to unwind, which is the whole point.
