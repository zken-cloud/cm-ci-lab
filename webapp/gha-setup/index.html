GitHub Actions Lab — Setup with Workload Identity

Wire the CodeMender pipeline to Google Cloud with no long-lived service-account key. GitHub mints a short-lived OIDC token, Google's STS federates it against a Workload Identity provider, and the run impersonates a service account in zken-genai. This page is the step-by-step setup; the GitHub Actions guide explains what the pipeline then does.

⏱ ~15 min ☁️ zken-genai 🔑 WIF · keyless ⚙️ ubuntu-22.04 · container ubuntu:20.04
⚙️ Why a container instead of a runner label

GitHub retired the ubuntu-20.04 hosted-runner label, so runs-on: ubuntu-20.04 no longer schedules a job. To get a real Ubuntu 20.04 userland the lab pins a supported runner and runs the job inside a ubuntu:20.04 container. The runner mounts its own Node for JavaScript actions, and Ubuntu 20.04's glibc 2.31 is new enough to run it — so actions/checkout and the auth action work normally.

◆

What you're given

Your instructor hands you four values. Exactly one is a secret; the other three are variables, because they are ordinary resource names rather than credentials.

NameKindLooks like
WIF_AUDIENCESecret//iam.googleapis.com/projects/163236863044/locations/global/workloadIdentityPools/github-pool/providers/cm-lab-provider
WIF_PROVIDERVariableprojects/163236863044/locations/global/workloadIdentityPools/github-pool/providers/cm-lab-provider
SA_EMAILVariablecm-lab-gha@zken-genai.iam.gserviceaccount.com
QUOTA_PROJECTVariablezken-genai
💡 WIF_AUDIENCE and WIF_PROVIDER are the same resource

The audience is just the provider path with an //iam.googleapis.com/ prefix — google-github-actions/auth derives it automatically when you omit it. The lab distributes both so the audience can be overridden centrally without editing every fork's workflow. Neither value is sensitive on its own: what actually gates access is the provider's attribute condition plus the IAM binding on the service account, so a leaked provider path grants nothing.

Instructor — one-time setup in zken-genai

Run once, before the session. Participants do not need any of this — skip to step 1 if you were handed the four values.

1 · Service account and APIs

2 · Workload Identity provider

The github-pool already exists in zken-genai. Add a dedicated provider for the lab rather than reusing an existing one — providers carry their own attribute condition, and the lab's condition must admit every participant fork.

⚠ The attribute condition is the security boundary

Without --attribute-condition, any GitHub repository on the internet can federate into your pool. Scope it to the org that owns the participant forks. If forks live under personal accounts instead of one org, either list them (assertion.repository in ['ownerA/juice-shop','ownerB/juice-shop']) or create one provider per participant.

3 · Let the pool impersonate the service account

📌 principalSet must match the mapped attribute

The member path uses attribute.repository_owner/<org>, which only resolves because step 2 mapped attribute.repository_owner. To bind a single fork instead, map and use attribute.repository/<owner>/<repo>. Use the project number here, never the project id.

4 · Print the four values to distribute

⚠ CodeMender CLI access is a separate entitlement

The cm binary is downloaded from Google's cmoc-prod Artifact Registry. Read access there is granted by your CodeMender preview contact, not by anything in this page. Confirm the lab service account can download the CLI before the session — that grant is the most common day-of blocker.

1

Add the secret and the variables

In your lab repo, go to Settings → Secrets and variables → Actions. The page has two tabs — put each value on the right one, or the workflow will read an empty string and fail with a confusing auth error.

  • Secrets tab → New repository secret → name WIF_AUDIENCE.
  • Variables tab → New repository variable → add WIF_PROVIDER, SA_EMAIL, and QUOTA_PROJECT.

Or with the GitHub CLI, from a clone of the repo:

💡 Secrets are masked, variables are not

Values in the Variables tab appear in plain text in logs. That is intentional here — they are resource names, and seeing them in the log is what makes a typo debuggable. Never move the audience or provider into the workflow file itself; keep them in repo settings so the instructor can rotate the provider without a commit.

2

Let Actions open pull requests

The pipeline pushes a codemender/fix-* branch and opens a PR with the built-in GITHUB_TOKEN. That is off by default.

  • Settings → Actions → General → Workflow permissions
  • Select Read and write permissions, and tick Allow GitHub Actions to create and approve pull requests.
⚠ Symptom if you skip this

Everything runs green until the last step, which fails with “GitHub Actions is not permitted to create or approve pull requests.” The scan and fix work is already done and lost — set this before the first run.

3

The workflow file

Create .github/workflows/codemender-setup-check.yml. This proves the whole trust chain end to end — federate, impersonate, install cm, and reach the CodeMender backend — before you spend 30 minutes on a real scan.

🔑 The three inputs to auth

workload_identity_provider names the provider to federate against, service_account is who you impersonate afterwards, and audience must match what the provider expects. Drop the audience line and the action derives the default — keep it only because the lab distributes it explicitly.

⚠ Pin actions/checkout@v4, not v5

v4 runs on Node 20, which Ubuntu 20.04's glibc 2.31 supports. Newer action majors move to newer Node runtimes; if one ever requires a glibc past 2.31 it will fail inside this container with a loader error rather than a clear message. Pinning majors keeps the 20.04 container predictable.

4

Run the setup check

Actions → codemender-setup-check → Run workflow. It should finish in about two minutes. Look for these three things in the log:

StepWhat proves it worked
authGreen, with Created credentials file at /github/workspace/gha-creds-*.json. That file holds a short-lived token, not a key.
Who am Igcloud auth list shows your SA_EMAIL as ACTIVE, and gcloud config list shows project = zken-genai.
Verify the CodeMender environmentcm init --verify prints Server connectivity and All critical checks passed. An empty build command warning is expected and harmless.
✅ What green means here

A passing check confirms federation, impersonation, quota attribution, CLI entitlement and backend reachability. It does not yet confirm the pipeline can open a PR — that needs step 2's repo setting, which the real workflow exercises on its last step.

5

Wire it into the real pipeline

Once the check is green, carry the same three blocks into the lab's pipeline workflow. Everything else — scan, triage, verify, fix, PR, gate — is unchanged and described in the GitHub Actions guide.

⚠ Delete the old key secret when you migrate

If the repo still has a GCP_SA_KEY secret, remove it (gh secret delete GCP_SA_KEY) and ask your instructor to delete the corresponding key in IAM. A migration that leaves the key in place keeps every risk WIF was adopted to remove.

🛠 Node and npm inside the container

The pipeline installs Juice Shop's dependencies so cm verify can build and run the app. In a bare ubuntu:20.04 container the distro's Node is far too old, so add actions/setup-node@v4 with node-version: 20 before npm install — it downloads its own Node and ignores the distro package.

Troubleshooting

Nearly every WIF failure is one of these six. The error text is the fastest way in.

ErrorCause & fix
Unable to get ACTIONS_ID_TOKEN_REQUEST_URLThe job is missing id-token: write. Note that declaring permissions at job level replaces the workflow-level block — if you set it in both places, the job block must list every permission you need.
Permission 'iam.serviceAccounts.getAccessToken' deniedThe principalSet binding doesn't match the token. Usually the repo owner differs from GH_ORG, or the binding used the project id where it needs the project number.
The given credential is rejected by the attribute conditionThe provider's condition excludes this repository. Check the fork's owner against assertion.repository_owner in the condition — a fork under a personal account will not match an org-scoped condition.
Invalid value for "audience" / audience mismatchWIF_AUDIENCE is wrong or was pasted into the Variables tab. It must start with //iam.googleapis.com/projects/ and use the project number.
PERMISSION_DENIED on aiplatform.googleapis.comFederation worked, authorization didn't. The service account is missing roles/aiplatform.user, or the API isn't enabled in zken-genai.
detected dubious ownership in repositoryThe container runs as root over a checkout owned by another uid. That is what the Trust the workspace step fixes — confirm it runs after checkout.
🔍 Read the claims the runner actually sent

When a condition rejects you and it isn't obvious why, print the token's claims. Add a temporary step before auth — it reveals the exact repository, repository_owner and sub your provider is matching against.

⚠ It prints an identity token — keep it out of shared logs

The decoded payload is claims only, but the raw $TOKEN is a live credential for its audience. Don't echo the token itself, and delete this step once the condition matches.

◆

Why WIF instead of a service-account key

The lab's earlier form used a GCP_SA_KEY secret — a JSON private key pasted into repo settings. It works, and it is the thing most CE conversations end up being about. The difference is worth being able to state precisely:

Service-account keyWorkload Identity
LifetimeValid until manually deleted — often yearsMinted per run, expires in about an hour
If it leaksUsable by anyone, anywhere, immediatelyUseless — a token is bound to the run that requested it
ScopeWhoever holds the file is the service accountOnly repos matching the attribute condition can federate
RotationManual, per repo, easy to forgetNone to do — there is nothing stored to rotate
RevocationDelete the key, then chase every copyEdit one attribute condition or IAM binding
AuditAll runs look like the same principalLogs carry the repository and subject that federated
🚨 The part people get wrong

WIF removes the stored credential, not the authorization. The service account still holds real permissions in zken-genai, and the attribute condition is the only thing standing between your project and any repository on GitHub. A provider created without --attribute-condition is strictly worse than a key: it is an open door with no file to delete. Scope the condition first, grant roles second.
