CodeMender Skills for Antigravity

An Agent Skill that drives CodeMender across a whole directory from Antigravity — find many vulnerabilities, verify them in parallel, fix the verified ones in parallel — each parallel worker isolated so the single-writer SQLite state never corrupts, and every cm run wrapped in an OS-native sandbox. All local, as you. No CI, no bucket, no secret store.

🧰 Agent Skill · SKILL.md ☁ <CM_PROJECT> · a project entitled to CodeMender 🖥️ macOS · Linux ◆ AGY CLI · 2.0 · IDE
✓ Why a skill instead of CI

The shared preview project only grants Vertex AI — no GCS or Secret Manager — so a Cloud Build pipeline can't run there. But you can run cm locally. This skill packages the fan-out + sandbox logic so Antigravity can drive it on your laptop, at scale.

1

Prerequisites

Everything runs locally as your own identity. You need:

  • cm on PATH — the skill can fetch it (scripts/bootstrap-cm.sh) or use the Smoke Test download.
  • Authenticated ADC, entitled to the preview.
  • git, jq, unzip on PATH; the target is a git repo.
  • Sandbox runtime — macOS sandbox-exec is built in; Linux needs gVisor runsc.
🔑 ADC survives the sandbox

Fan-out workers each run with a private HOME (for an isolated state.db), which would normally hide your ADC. The skill pins GOOGLE_APPLICATION_CREDENTIALS to your real ADC file up front, so auth keeps working — nothing to configure.

Linux only — install gVisor (rootless, no Docker; works without KVM via the systrap platform):

2

Install the skill

An Antigravity skill is a folder containing SKILL.md plus its scripts/. Drop codemender-fanout/ into one of the two universal skill locations — both are recognised by AGY, AGY CLI, and AGY IDE (2.0 included).

◆ One skill, all three AGY surfaces

AGY, AGY CLI, and AGY IDE share the same SKILL.md format and each read the two locations above — so a single install covers the CLI, 2.0, and the IDE. (Variant-specific paths also exist — ~/.gemini/antigravity/skills/, ~/.gemini/antigravity-cli/skills/ — but the two universal ones avoid the guesswork.)

Use it from Antigravity

Open the target repo in Antigravity (CLI, 2.0, or IDE) and ask the agent for the task — it discovers codemender-fanout by its description, reads SKILL.md, and runs the scripts. A prompt like:

The agent sets REPO_DIR/SCAN_PATH, runs find.sh → verify.sh → fix.sh, and reports the results. On Linux it will pass SBX_RUNSC_FLAGS=--rootless for an unprivileged laptop.

💡 First time? Ask it to bootstrap

“First run scripts/bootstrap-cm.sh if cm isn't installed, then verify auth with cm init --verify.” The skill's SKILL.md already documents this so the agent does it in order.

4

Run the scripts directly

The same scripts work standalone — handy to smoke-test the skill before wiring it into the agent. Point at a repo and a scan path, then run the three phases in order.

⚠ Confirm cm -c before scaling fan-out

Each worker asks cm to run the app on a unique port via -c context, so verify/fix parallelise without colliding. If your cm expects a structured context instead of free text, set CM_CTX_TEMPLATE="<key>=%PORT%" (or CM_CTX_TEMPLATE="" to disable and keep fan-out at 1). Start with a single verify before raising VERIFY_FANOUT.

How the fan-out stays safe

Isolated SQLite state

cm keeps findings in a single-writer SQLite state.db. find writes it once; then verify/fix fan out and each worker copies the state to a private dir and runs in its own independent git clone (a shared git worktree deadlocks on .git/index.lock). Results come back through append-only hand-off files, never a concurrent DB write.

Unique port per worker

cm verify/cm fix build and run the target app to reproduce the exploit — on a fixed port by default. Each worker derives a deterministic unique port from the FindingID and passes it via cm -c, so parallel workers don't collide on either OS.

Sandbox per OS

OSSandboxWhat it contains
macOSsandbox-execReads/exec/network allowed; writes confined to the worker dir + tmp. Built in.
LinuxgVisor runsc doIntercepts syscalls (protects the host kernel) and isolates the network. No Docker. tested
✓ Validated on Linux through real gVisor

The full flow — find → parallel verify → parallel fix, with per-worker state copies, independent clones, unique ports, and the hand-off files — was run end-to-end through runsc (rootless, systrap). Two Linux notes: runsc do overlays the host read-only, so the wrapper uses -force-overlay=false to persist the hand-off files (gVisor still isolates syscalls + network, but not filesystem writes to a subtree the way macOS does); and per-worker netns needs root, so on a rootless laptop the unique port is what keeps parallelism safe.

Tuning & troubleshooting

Env varDefaultMeaning

SKIP_EXPLOIT01 → static verify (no app, no port)
CM_CTX_TEMPLATEport instruction-c template; %PORT% placeholder; "" disables
SBX_RUNSC_FLAGS—Linux: set --rootless on an unprivileged laptop
SBX_DISABLE01 → run unsandboxed (loud warning; unsupported hosts only)
  • Unsupported agent interaction: codemender-preview — your ADC identity/quota project isn't entitled. Re-check the auth step.
  • Linux: runsc: permission denied — set SBX_RUNSC_FLAGS=--rootless.
  • Port collisions when fanning out — cm -c isn't honouring the port; fix CM_CTX_TEMPLATE or drop fan-out to 1.
